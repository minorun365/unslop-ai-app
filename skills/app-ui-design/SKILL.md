# AIが作った感じのしないアプリ画面

AIに画面を作らせると、頼んでいない部品が増え、同じ型の飾りが並び、見出しが宣伝文になる。どれも1つずつは親切に見えるが、合わさると「AIが作った画面」と一目で分かる。この規則は、その型を作る前に避け、作った後に機械で拾うためのもの。

対象は業務で使うアプリの画面（ダッシュボード、チャット、管理画面、デモアプリ）。読ませる資料やランディングページは別の作法なので、ここでは扱わない。キャラクターを主役にした遊びのある画面では、口調の「！」や意図した動きを残してよい。その行には `check-ui-ignore` を書いて検査から外す。

## 進め方

1. **作る前に、画面の主役を1文で書く。** 「この画面で利用者は何を見て、何を押すか」。主役が2つ以上になったら画面を分ける
2. **部品を足す前に「これが無いと使えなくなるか」を問う。** 答えが「無くても使える」なら置かない。頼まれていない部品は、作る代わりに提案として1行で伝える
3. **下の「AIらしく見える型」を避けて書く**
4. **出す前に検査を通す。頼まれなくても自分で走らせる。** 画面を作った・直したら、`node ~/.claude/skill-repos/unslop-ai-app/tools/check-ui.mjs <画面のソース>` を当て、指摘を0件にする（見つからなければ、このスキル集を入れたリポジトリの `tools/check-ui.mjs`）。続けて実際の画面を開き、下の「出す前に見るところ」を確かめる。利用者に検査の名前やコマンドを打たせず、結果は「AIらしく見える書き方が◯か所あったので直した」のように平易な言葉で伝える
5. **既存の画面を直したときも、同じ画面の残りの型を探して直す。** 指摘された1か所だけ直すと、同じ型が隣に残る

## 1. 情報の引き算

- **主要な出力と、それを読むための一言だけにする。** 内訳、表示切替のトグル、見出し横のバッジ、補助のリンク（「全画面で開く」など）は頼まれるまで置かない。閲覧に要らない要素は、主役の面積を削るだけになる
- **数字の補足を足さない。** 処理時間、経過時間、件数、接続状態の点は、頼まれるまで出さない。出すなら「この数字を見た人が何を判断するか」を1行で言えるものだけ
- **要約の数字のカードには、見出しと数字だけを置く。** その下へ内訳の件数や説明文を並べない。補足が要るなら1点に絞る
- **カード1枚に情報を詰めない。** 詰まってきたら、カードを増やすより画面を分ける
- **設定のチェックボックスやオプションを、操作する画面に並べない。** 開発や検証にしか使わない切り替えは URL のパラメータへ逃がし、既定値を本番の値にする
- **引くのは情報で、作りの厚みではない。** 製品らしさを出す面・影・アイコン・状態に応じた色や動きまで削ると、今度は「簡素すぎて安っぽい」画面になる。出す前に「要らない情報が無いか」と「製品の画面に見えるか」の両方を確かめる
- **サイドバーは折り畳めるようにする。** PCでも本文を広く使いたい場面がある

## 2. AIらしく見える定番の型

見つけたら直す。左が型、右が直し方。

| 型 | 直し方 |
|---|---|
| カードや枠の1辺（左端・上辺）だけに太い色の線を付ける | 面は白か淡い地、角丸、薄い影、細い枠で作る。種類や状態は小さな丸か文字で示す |
| 枠の中に、さらに「色付きの地＋太い左線＋角丸」の小箱を並べる | 文字の太さ、行間、段落の間隔で読ませる。箱の入れ子をやめる |
| 絵文字をアイコン代わりに並べる（🚀 🔥 💡 ✅ ⚠️） | 線のアイコン素材を1種類だけ使う。数も絞る。要らなければ何も置かない |
| AIの機能にきらめき（✨）や光る球を付ける | 外す。AIが出した結果そのものを見せる |
| 四角い塗りの番号バッジ（角丸チップに白抜きの数字） | 数字は文字のまま置き、罫線で区切る |
| 見出しの下に小さい文字の注記をもう1行足す | 消す。必要な説明は本文の1行目へ |
| 光る影（色付きの `box-shadow`）、ネオン色の枠、ぼかした色の円を背景に置く | 外す。奥行きは地の明るさの差と細い線で作る |
| 文字にグラデーションをかける | 単色にする |
| 紫から青、青からピンクの派手なグラデーションを、ボタンや背景に広く敷く | 地は無彩色にし、強い色は意味のある1〜2か所だけ |
| 何もかもを丸い錠剤形（ピル）にする | 部品の大きさに合わせて角丸の半径を変える |
| 「NEW」「PRO」「Beta」のバッジを散らす | 外す。本当に必要な1つだけ、目立たない文字で |
| 同じ大きさのカードを横に並べ、全部に同じ小さなグラフを入れる | 主役のグラフを1つ大きく置き、残りは数字だけの小さな表示にする |

## 3. 画面の文言

- **見出しは、その場所で何をするかを名詞で示す。** 「釣行の予定」「相談の履歴」「設定」「ログイン」のように書く。キャッチコピー、対句、比喩、飾りの英字見出し、使っている技術の名前は入れない
- **キャッチコピーを消すときは、別のキャッチコピーへ言い換えない。** 機能名へ戻すか、要素ごと消す
- **空の状態を待機メッセージで埋めない。** 「ここに結果が表示されます」「◯◯を準備中…」は置かず、何も出さないか、次に押すものだけを示す
- **あいさつの見出しを置かない。** 「ようこそ、◯◯さん！」のような見出しは、画面の名前か対象の期間に替える
- **「！」を付けない。** ボタン、見出し、通知のどれも平叙で書く
- **増減には比べる相手を書く。** 「+12%」ではなく「前月比 +12%」
- **入力欄の案内文は短く。** 「何でも聞いてください…」ではなく「質問を入力」
- **ボタンは動作の名前にする。** 「送信」「保存」「削除」。「さっそく始める」「今すぐ試す」のような誘い文句にしない
- **ボタンや短いラベルの末尾に句点を付けない**
- **効能を盛る言葉を使わない。** 「爆速」「シームレス」「革新的」「魔法のように」。何をするのかを書く
- **作り物に見える値を置かない。** `12,345` や `XXX` のような見本の値は、ありそうな値にする。架空の値でも桁と端数を自然にする

## 4. 色

- **基調の色相は1つ、それに無彩色（黒・白・グレー）と、強調の色を1つ。** 区分ごとに赤・緑・紫・橙と色を変える多色の塗り分けはしない。強弱は太さ、大きさ、罫線、地の濃さで付ける
- **強調の色は「面」ではなく「点」で使う。** 1画面に数か所まで
- **文字色は「主」「副」「控えめ」の3段階だけにする。** 少しずつ違うグレーや淡い色を何種類も作らない
- **枠線は、主な文字色を 6〜10% の透明度にした細い線にする。** 蛍光色や強いコントラストの枠線は使わない
- **良し悪しの色（増加の緑、エラーの赤）は意味があるときだけ使い、彩度を落として全体になじませる**
- **色はすべて CSS 変数に集める。** 部品に色を直接書かない。調整が変数の差し替えで済む
- **相手先のブランド色を使う画面は、白基調に、その色を必要な所だけアクセントで入れる。** 色の値は推測せず、公式サイトの実際の値を取る
- **文字色と地の色は、同じ詳細度の1つの規則にまとめて書く。** 文字色と地の色を別々の規則で当てると、置き場所によって片方だけ上書きされ、白地に白文字のように読めなくなる。広いセレクタ（`p`、`code`）に色を当てる場合は、画面の外枠のクラスで範囲を絞る
- **濃い地の上に半透明の下敷きを置くなら、暗くする色にする。** 明るい半透明の下敷きは、グラデーションの明るい側で白文字を消す
- **コントラストは目で判断せず、測る。** 本文の文字と地の明度比は 4.5 以上、大きい太字なら 3 以上。測り方は `references/contrast.md`
- **同じ色でも、面は明るく、細い線や文字は暗く見える。** 面と文字に同じ色を使って「文字が沈む」と言われたら、文字用の色を1〜2段明るく（白地なら暗く）分ける
- **2色が喧嘩するときは、色相より先にトーン（明度と彩度）をそろえる。** 色相を動かすと色の意味まで変わる（黄の強調を緑にすると「完了」に読める）
- **「メリハリがない」と言われたら、主役ではなく周りを落とす。** 見出し、罫線、ラベルの明るさを段階的に下げる。差は倍々くらいで付けないと、変えた気がしない
- **候補の色は、実際の画面に当てて並べて見せる。** 色見本や数字だけでは決まらない
- **ダークテーマは頼まれたときだけ。** 既定は白い地に濃い文字

## 5. 日本語の組版

- **フォントは OS の日本語ゴシックを先頭に並べる。** `-apple-system, BlinkMacSystemFont, "Hiragino Sans", "Noto Sans JP", sans-serif`
- **本文は行間を広めにとる**（`line-height: 1.7〜1.85`）。英語向けの既定（1.5）のままだと日本語は詰まって見える
- **約物を詰める。** `font-feature-settings: "palt" 1` を見出しと本文に入れる
- **太さは2段階まで。** 本文の 400 と、見出しの 600〜700。800 以上の極太を見出しに使わない
- **英字のラベルを大文字にして字間を広げる飾りを使わない。** 日本語の画面では意味のない飾りになる
- **小さい文字に負の字間を付けない**
- **数字は桁をそろえる。** 表や集計の数字には `font-variant-numeric: tabular-nums` を付け、同じ種類の数字は書式（桁区切り、小数の桁）をそろえる
- **斜体を使わない。** 日本語の書体には本来の斜体が無く、機械的に傾くだけになる
- **改行位置を見る。** 見出しやカードの末尾で2〜3文字だけが次の行へ落ちたら、文字を縮めず、見出しを短くするか残りを本文へ移す

## 6. 余白と配置

- **余白は 4px の刻みにそろえる。** `13px` や `7px` のような半端な値を使わない
- **同じ種類の部品は、同じ高さ、同じ内側の余白にする**
- **まとまりの内側は狭く、まとまりの間は広く。** 隣のまとまりとの間隔が、内側の間隔より狭くなっていたら直す
- **縦に並ぶ別々のブロックの間は、16〜24px を明示する。** グリッドの `gap` が付くのは、グリッドの中の要素どうしの間だけ。グリッドと次の表の間などは、隣接セレクタ（`.grid + .table-wrap { margin-top: 20px }`）で間隔を付ける
- **内側の余白は密度で決める。** 詰まった面（サイドバー、ナビゲーション）は 16 前後、カードは 20〜24、ページの端は 24〜32。ナビゲーションの行は高さ 32〜36、行の間は 2〜4
- **アイコンは1列、ラベルは1本の線、数字は右揃えの1列に並べる。** `translate` や半端な余白で1つだけずらさない
- **入れ子の角丸は、外側の半径 = 内側の半径 + 間の余白にする**（内側は 4 未満にしない）
- **比べる2列は上下の端をそろえる。** 中身の量が変わる画面では、両方に同じ高さを与えて中をスクロールさせる

## 7. アイコンとグラフ

- **アイコンの絵柄集は1つにそろえる。** プロジェクトに既存のものがあればそれ、無ければ lucide。大きさは 16 か 18px、線の太さ 1.5
- **アイコンの色は、横の文字と同じ役割の色にする。** アイコンごとに色を付けない。アイコンの枠の幅とラベルまでの間隔（8 か 10）を全行でそろえ、ラベルの頭を1本の線に並べる
- **主役のグラフを1つ決めて、画面でいちばん大きく描く。** ほかのデータは小さく、種類を変える（細い棒の付いた順位の一覧、短い表）。同じ大きさのグラフを2つ並べない
- **1つのグラフの強調は1か所だけ。** 今月、追っている系列など見せたいものに強調の色を使い、残りはグレーの段階で描く。1つの系列の中で棒ごとに色を変えない
- **グラフの種類はデータで選ぶ。** 推移は折れ線、比較は棒、割合は1本の積み上げ棒か棒付きの一覧、1つの目標は進捗バー。補助線は淡く、軸のラベルは控えめな色の等幅の数字にする
- **要約の数字のカードに、小さなグラフや棒、アイコンを埋め草として足さない。** 見出し、大きな数字、比べる相手付きの増減の3つで足りる
- **同じ幅のカードを横に並べるだけの配置を避ける。** 数字のカード3〜4枚の下に横長のグラフ1つ、幅の広いグラフの横に細い一覧、のように幅に強弱を付ける

## 8. 動き

- **常に動いている飾りを置かない。** 点滅、脈打つ光、浮遊する要素は、実際に進行中のものにだけ使う
- **`transition: all` と、カードの拡大のホバーを使わない。** ホバーでは地の色を1段変えるだけにする
- **跳ねる動き（スプリング、行き過ぎて戻る動き）を使わない。** 動きの曲線は ease-out の1種類にする
- **読み込み時に、あちこちから要素を飛び込ませない。** 使うなら、短いフェードと少しの上昇だけ
- **幅、高さ、位置（`top` `left`）を動かさない。** `transform` と `opacity` で動かす
- **動きの曲線と長さを画面全体でそろえる。** 曲線は `cubic-bezier(0.22, 1, 0.36, 1)` の1本。長さはホバーと押下が 120〜180ms、メニューが 160〜220ms、登場が 300〜500ms。押したときの縮みは 0.97〜0.98 倍まで
- **状態に応じた動き（話している人の波形、処理中の表示）は残す。** 引き算の対象は飾りの動きで、意味のある動きではない

## 9. 操作の作り

- **ホバーとフォーカスの状態を必ず作る。** キーボードで操作する人のために、フォーカスの枠を見えるようにする

- **既にある部品の役割を広げない。** 絞り込みのチップは絞り込むだけ、星は印を付けるだけ。「この項目には行き先が無いから、代わりに別の画面を開けば親切だろう」という例外の挙動は、押した人には誤動作に見える。導線が要るなら、部品の外にリンクとして置く
- **外部サービスとの「連携」を名乗るなら、取得と登録の両方をAPIでつなぐ。** 片方が利用者のコピーと貼り付けなら、それは連携として主導線にしない。手入力は、権限不足や障害のときの補助へ下げる
- **メニューはホバーではなくクリックで開く。** タッチ端末ではホバーが働かない。外側を押したら閉じる
- **確認、処理中、結果の3段階を持つダイアログは、処理が終わってから閉じる。** 先に閉じると「処理中」が見えない
- **他の人が使っている本番の画面は、合意の前に見た目や挙動を変えない。** 消す方向の変更も同じ。改善の案は実装せずに提案する
- **人前で操作する画面（発表、デモ、画面共有）は、別の作法がある。** `agent-app-ui` スキルの「人前で使う画面」節を読む

## 10. 出す前に見るところ

`tools/check-ui.mjs` は書き方の型を拾う。残りは実際の画面を開いて見る。

1. **画面の全種類を開く。** トップだけ直して、子画面やダイアログに古い型が残るのはよくある
2. **指摘された所だけでなく、画面全体を一度なめる。** 上端、浮いている要素と本文の重なり、余白の偏り、下端、横へのはみ出し（`scrollWidth === clientWidth`）
3. **コントラストを測る**（`references/contrast.md`）
4. **製品名を別の製品に入れ替えても成り立つ画面か、を問う。** 成り立つなら、まだテンプレートの見た目。文言、主役の見せ方、色のどれかに、その製品だけのものを入れる。外した飾りの代わりに、別の流行の飾り（すりガラス、ノイズ、ネオン、タイル状のカード並べ）を足していないかも見る
5. **スマホでも使う画面なら、`mobile-web-check` スキルの手順で実機相当の検証をする**
